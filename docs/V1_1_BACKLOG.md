## P2

### 첫 방문마다 빈 여행이 서버에 생성된다
- 문제: 앱을 처음 열면 로컬 첫 실행용 빈 여행(`새 여행`)이 곧바로 D1에 `trips`·`members`·`sessions` 행으로 동기화된다.
- 재현: 데이터가 없는 브라우저로 운영 주소 접속 → 클릭 없이 `trips` 행 1건 생성.
- 사용자 영향: 없음(화면은 정상적으로 첫 실행 안내를 보여준다). 운영 영향: 방문/크롤러마다 빈 여행이 누적된다. 운영 D1 기준 `trips` 93건 중 실제 일정이 있는 여행은 소수(전체 `items` 13건), `members` 233건·활성 `sessions` 230건.
- 제안: 사용자가 제목·기간을 저장하거나 첫 데이터를 입력할 때까지 서버 생성을 미루고, 그때 세션을 만든다.
- 복잡도: 중 (sync bootstrap과 첫 실행 흐름 수정)

### 서버가 영구 거부하는 outbox 항목이 계속 재시도된다
- 문제: 400처럼 재시도해도 성공할 수 없는 응답에도 outbox 항목이 남아 매 동기화마다 같은 요청을 반복한다.
- 재현: 잘못된 시간(`010:00`)이 든 상태를 IndexedDB에 주입 → 새로고침마다 `POST /api/trips` 400 반복.
- 사용자 영향: 정상 UI 입력에서는 클라이언트 검증이 막아 주지만, 손상된 캐시나 오래된 백업 복원 뒤에는 동기화가 영구히 대기 상태로 남는다.
- 제안: 4xx(409 제외) 응답은 재시도 대상에서 분리하고, 진단 화면에서 `확인 필요` 상태와 오류 코드를 보여준 뒤 사용자가 수정하도록 한다.
- 복잡도: 중

### production smoke가 비정상 종료하면 검증용 여행이 남는다
- 문제: 정리는 `finally`의 API 삭제에만 의존한다. 프로세스가 중간에 끊기면 남는다.
- 근거: 운영 D1에 2026-08-29 실행분 `smoke_1788015414271`이 삭제되지 않은 상태로 잔존(그 외 61건은 정상 삭제).
- 사용자 영향: 없음. 운영 데이터 위생 문제.
- 제안: smoke 시작 시 하루 이상 지난 `smoke_%` 여행을 정리하는 단계를 추가한다.
- 복잡도: 하

### 사용하지 않는 아이콘 원본이 배포에 포함된다
- 문제: `assets/icons`의 v3~v7 후보와 `icon-source*.png`까지 `dist`로 복사된다. 실제 참조는 v8 세트뿐이다.
- 근거: `dist/assets/icons` 약 8MB, 이 중 참조되는 파일은 4개.
- 제안: 빌드에서 참조되는 아이콘만 복사하거나 후보 파일을 별도 디렉터리로 분리한다.
- 복잡도: 하

## P3

### 앱 셸 캐시에 `/`와 `/index.html`이 중복 저장된다
- 문제: Static Assets가 `/index.html`을 `/`로 307 리다이렉트하는데 Service Worker는 두 경로를 모두 프리캐시한다.
- 근거: 운영 브라우저에서 `yeogiro-app-v77` 캐시 항목 20개 중 `/`, `/index.html` 동시 존재.
- 사용자 영향: 없음(설치·오프라인 정상). 캐시 용량만 중복.
- 제안: 프리캐시 목록에서 `/index.html`을 빼고 navigate 폴백만 유지한다.
- 복잡도: 하

## 성능 기준선 (2026-09-05, 로컬 Worker + Chromium 320x568, build v1.0.0 · 4a093e8)

`tests/e2e/full-journey.e2e.mjs`가 매 실행마다 다음 수치를 출력한다.

- 데이터량: 여행 10개 · 일정 500개 · 경비 1000건 상태에서 첫 렌더 187~783ms, 검색 314~597ms (실행 환경 부하에 따라 변동)
- 중복 요청: 이동 화면 진입 후 일정 화면 복귀까지 API 호출 1건, 여행 동기화 1건
- 동일 조건의 날씨·환율 요청이 한 화면 진입에서 반복되지 않음을 단정한다.

날씨는 지역·날짜 키로 30분 캐시와 진행 중 요청 공유(`weatherRequests`)를 사용하고, 경로는 메모리 캐시 7일 + IndexedDB 캐시를 사용한다. 좌표가 없으면 요청을 보내지 않는다(v1.0 수정 이후).

## 다음 신규 기능 사전 검토 — 여행 기록·사진 연결

저장 정책을 먼저 정하고 UI는 그 다음이다.

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 기기 로컬(IndexedDB)만 | 기존 예약서류 정책과 동일, 추가 비용 없음, 오프라인 즉시 열람 | 다른 기기·동행자는 원본을 볼 수 없음, 기기 분실 시 백업 의존 |
| R2 등 공용 객체 저장소 | 공유 여행에서 모든 참여자가 같은 사진을 봄, 기기 교체에 안전 | 비용과 권한 설계 필요, 삭제·정산 정책 필요, 오프라인 열람은 별도 캐시 필요 |

- 추천: 1차는 로컬 원본 + 메타데이터만 동기화(예약서류와 동일한 정책). 다른 기기에서는 자리표시자와 안내를 보여준다.
- 결정이 필요한 사항: 공유 여행에서 사진을 모든 참여자가 봐야 하는지, 여행당 저장 상한, EXIF 위치·촬영시각·원본 파일명 제거 범위, 여행 삭제 시 원본 정리 시점.
- 1차 범위 후보: 일정에 사진 연결, 대표 사진 선택, 여행 기록 화면의 날짜별 사진, 사진 삭제·교체. 앨범·자동 편집은 범위 밖.
